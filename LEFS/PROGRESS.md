`parse --qcmd` 只解决「对齐」，不解决「跟上」。而「跟上没跟上」正是 R19 的判据，也是 L1 会不会学成恒等映射的分水岭。所以新增子命令：

```
python stage1_l0.py track episodes/l0b_j6/samples.jsonl --out episodes/l0b_j6
```

逐关节给四样东西：**响应比**（std(q)/std(q_cmd)）、**最佳滞后**（让 RMSE 最小的指令平移，就是实测延迟）、**RMSE@0 vs RMSE@best**、**dq/∂q_cmd**（实测转速峰值 vs 指令数值微分峰值，用来验 0.001 rad/s 这个量纲）。三类结论分开：

- `未跟随（R19 嫌疑）`：有指令、几乎不动 → 直接拦在 L1 门口
- `跟随`：幅度跟得上
- `未激励`：指令本身峰峰 < 0.5° → **不判「没跟随」**，因为这一路压根没被激励；把它混进去会让「六轴里有四轴没动」看起来像故障

本地用合成样本验过三条分支：给 100 ms 纯滞后 → 判 `跟随`、滞后 **100.0 ms**；q 恒定 → `未跟随`；q_cmd 恒定 → `未激励`。`selftest` 仍 PASS 8/8。

- **R18**：首帧守卫在恒定零值上假阳性，`opened=True` 但数据是假的

新开两条（同型：都是"看起来正常、其实数据已经错了"）：

- **R30**：并发「录制+下发」时录制端断流，90.2 s 只覆盖 52.0 s。**按墙钟算会得出"丢 42%"，按帧跨度算是 199.9 Hz 一帧没丢** —— 判据分母错，结论就整个反过来。阶段 3 必须同时录+发，所以这条是阶段 3 的前置条件
- **R31**：`JointCtrl()` 返回 `None`，发送失败只在 SDK 自己 logger 里留一行 → CSV 把 80 帧没发出去的指令记成了真指令。2.0 起自建 socket 逐帧判定，失败不写 CSV
- **R32**：`EnableArm(7)` 的 7 语义矛盾（手册=六关节+夹爪 / SDK 消息=仅夹爪，全部是 0xFF）
- **R33**：`GripperCtrl()` 与 `JointCtrl()` 同型，返回 `None`，失败只打日志 → 会把「没发出去」误判成「夹爪不响应」
- **R34**：`ip link set can0 up type can bitrate 1000000` 一体化写法报 `No such device`，实际是 netdev 半提交，拆三步才成 → 报错文案指错方向（本次被误导一轮）
- **R35**：24 V 与 CAN 在同一个 7 芯航插里（pin4/5=电源、pin6/7=CAN）；「面板灯亮」≠「主控就绪」，官方判据是**绿色慢闪** → 会把「主控没 boot」误判成「上电成功」
- **R37**：`0x1C1` 以 40 Hz 常驻，CAN 手册与 SDK 均无定义（属 `0x1xx` = 节点 ID 1 主控板段）→ 不应被当成「未知设备接入」，也不该被计入异常
- **R36**：全总线静默（0x251~0x256 与 0x2A1~0x2A8 同时为 0）且 `RX errors=0` → 不是波特率错、不是 H/L 反接，是线上没有差分信号；排查面收窄到「主控没发」或「CAN 对开路」
