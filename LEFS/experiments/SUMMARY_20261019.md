## 1 一句话结论

**信号链已经从「能收到帧」验到「速率级复现 + 零丢帧 + 指令真的驱动了臂」。**
总线上 3138 帧/秒、六路高速反馈各 199.8 Hz；六轴 ±2° 正弦下发后六轴全部跟随（响应比 0.939~0.942）；并发「录制 + 下发」跑满 75 秒、`RX/TX` 的 `dropped/overrun/errors` 前后全为 0。

这意味着 FACTR 2 复现里最容易被忽略、也最容易埋雷的一段（PC ↔ CAN ↔ 臂的时序与同步）已经闭合，可以从「机械臂能按指令动、数据能对齐」这个前提出发进入力矩标定。

### 2.1 固件实测限位（`0x473`）

| | J1 | J2 | J3 | J4 | J5 | J6 |
| --- | --- | --- | --- | --- | --- | --- |
| 下限 (°) | −150 | 0 | −170 | −100 | −70 | −180 |
| 上限 (°) | +150 | +180 | 0 | +100 | +70 | +180 |
| 最大速度 | 0.300 rad/s | 同左 | 同左 | 同左 | 同左 | 同左 |

- 与 URDF 逐关节对照：**J1–J5 完全一致**（≤0.1°，即 `0x473` 的 0.1° 步长）；**仅 J6 不一致**（固件 ±180° vs URDF ±120°）。
- 因此限位包络取**固件 ∩ URDF**，J6 被收紧到 ±120°（`stage1_cmd.py` 已实现）。
- 速度上限 0.300 rad/s 由 SDK 源码 `piper_interface.py:3200` 定案（unit 0.001 rad/s、Range [0,3000]），不是「读出来看着像」的推断。

### 2.2 门 9 为什么可以「有条件」闭合

官方三方交叉数据一致：本体 4.2 kg、额定负载 **1.5 kg（含末端工具）**、从动夹爪 **500 g**、主动夹爪/示教器 550 g、装标准夹爪后可搬物约剩 1.0 kg。

现场没有秤，按指南 §2.3 的规则（**「未知项写未核验，不要填一个看起来精确的默认值。伪精确比空白更危险」**），实测值保持 `null`，官方标称单独登记为「未实测」。

不阻塞阶段 2 的理由：静态差分 `I₁ − I₀ = K ⊙ Δτ_ref` 中，末端重力项在两次测量里同样存在、**差分时被消掉**，剩余部分被 K 的整体增益吸收。末端质量的绝对值不是标定的必需输入，只用于判断「K 的量级是否物理合理」。阶段 2 本来就必须称已知质量砝码，届时**顺手把末端一起称**即可闭合。

## 3 阶段 1（L0）：信号链与同步

### 3.1 L0-a 被动录制（660 s）

| 判据 | 结果 |
| --- | --- |
| 帧数 / 时长 | **2 073 061 帧 / 660.2 s = 3141 帧/s** |
| 六路高速反馈 | `0x251~0x256` 各 **132 000 帧**、周期中位 **5.0 ms（199.94 Hz）** |
| >100 ms 空档 | **0** |
| 六轴齐备率 | ≥99.9% |

**单位定案（R12）**：`0x251` 位置字段 / `0x2A5` 角度字段 = **999.893**，即 `0x251` 的单位是 **0.001 rad**（指南 §4.2 写的 rad 小了 1000 倍）。后续在 16:45 的六轴录制里又以 mrad 口径复算得 **0.998**，与 999.893 互为倒数 —— **两条独立数据路径互证，此条不再反复验**。

**q 只取 `0x2A5~0x2A7`**（关节角，度），不使用 `0x251`。

### 3.2 L0-b 主动下发

| 项目 | 单轴（J6）15:26 | 六轴 16:45 |
| --- | --- | --- |
| 轨迹 | ±3° @0.1 Hz | 六轴同相 ±2° @0.1 Hz / 60 s |
| 判定 | **跟随**（响应比 0.8672、滞后 60 ms） | **六轴全部跟随**，响应比 0.9391 / 0.9403 / 0.9409 / 0.9420 / 0.9416 / 0.9407，滞后 80/80/80/60/60/60 ms |
| 结论 | **R19 关闭**：指令真的驱动了臂 | **R19 在六轴模式下同样关闭** |

六轴响应比离散度只有 **0.3%**，说明这是**系统性约 −6% 衰减**，不是某一轴的问题。单轴的 0.8672 与六轴的 0.9407 不同，因为幅值/工况不同 —— **0.87 不能当基线用**。

**滞后值的限制**：60 / 80 ms 恰好都是 50 Hz 重采样栅格（20 ms）的整数倍，**分辨率不足**。L1 做时间对齐前必须做亚采样插值，否则会把栅格量化误差当成物理延迟补偿掉。

**工具设计里继承的教训**（每条都对应一次真实误判）：

1. **自建 socket 逐帧判成败**，不用 SDK 的 `JointCtrl()`（无返回值，R31）；发送失败不写 CSV、不推进 `q_prev`，连续 30 拍 ABORT。

## 7 现场事故与排查方法论

今天遇到并解决的四次「总线/接口」故障，共同构成一条可复用的排查链：

| 现象 | 曾经以为 | 真实原因 | 定案依据 |
| --- | --- | --- | --- |
| `0x2A8` 零帧 | 夹爪坏了 | **整条总线 netdev 已失效**（与夹爪无关） | 同时 `--phase bus` 0/6 + `ip -s` RX 仅 4 帧 |
| `ip link set can0 up type can bitrate ...` → `No such device` | USB 直通断了 | can0 netdev **半提交**（dmesg 连打三条 link change failed） | `lsusb` 一直有 `1d50:606f`、`gs_usb` 一直加载 |
| 全总线静默、`RX errors=0` | 波特率/H-L 反接 | **线上没有差分信号**（主控没发或 CAN 对开路） | 若对端在发而参数不匹配，`errors` 会涨；恒 0 说明线上安静 |
| `ModuleNotFoundError: piper_sdk` | 脚本 bug | 新终端**没进 `ros` 虚拟环境**（提示符没有 `(ros)`） | `conda` 命令不存在、`~/miniconda3` 不存在 ⇒ 是 venv 不是 conda |

**方法论沉淀（三条）**：

1. **「有帧」不等于「设备被识别」**：无夹爪时 `0x2A8` 同样 200 Hz、只是载荷全 0，是臂侧占位帧。
2. **成功的那部分会掩盖失败的那部分**：一条命令里 `6/6 命中` 与 `SDK 未加载` 可以同时出现（R27/R31 同型，今天出现了第三次）。
3. **先用单帧 ACK 探测再动机械**：发一帧 `0x7FF`（不在任何 PiPER ID 段），`TX errors` 不涨 ⇒ 有节点 ACK ⇒ 电气层在线。这比查线、比万用表都快。
